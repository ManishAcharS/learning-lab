## Implemented features and files

### 1. JWT access-token utilities

**File:** `security.py`

`create_access_token(subject, secret_key, expires_delta=None)` creates an HS256 token with only `sub`, `iat`, and `exp`. It rejects an empty subject or signing key and defaults to a 30-minute lifetime. `decode_access_token()` requires all three claims, accepts only HS256, and validates the signature and expiry through PyJWT.

Relevant tests in `test_security.py` verify that expired tokens raise `jwt.ExpiredSignatureError`, tampered tokens and wrong-secret tokens raise `jwt.InvalidSignatureError`, and non-HS256 tokens raise `jwt.InvalidAlgorithmError`.

### 2. Password hashing and registration

**Files:** `security.py`, `models.py`, `main.py`, `database.py`

Passwords are hashed with Argon2id through `pwdlib`. Hashing the same password twice produces different `$argon2id$...` hashes, proving a unique salt. `User.hashed_password` is the only stored password field. `POST /auth/register` hashes the password, normalizes the email, returns only `id`, `email`, and `created_at`, and returns `409` with `{"detail": "Email already registered"}` for duplicates.

`test_auth.py` verifies successful registration, email normalization, duplicate-email handling (including case/whitespace), invalid email/password rejection, database persistence, Argon2id hashing, and absence of plaintext or hashes in responses.

I also checked the legacy migration path in `migrate_task_ownership.py` against a temporary SQLite database. A dry run reported the intended owner but changed nothing. A real run against the temporary copy preserved both legacy rows with their original IDs and `created_at` values, backfilled `user_id`, created `ix_tasks_user_id`, and produced no foreign-key violations.

### 3. Current-user authentication dependency

**Files:** `deps.py`, `main.py`

`get_current_active_user()` extracts the Bearer token with `OAuth2PasswordBearer`, reads the signing key from `TASKFLOW_JWT_SECRET`, validates the JWT, requires a decimal subject within SQLite's signed 64-bit range, loads the user by ID, and returns the ORM user. Missing, malformed, expired, tampered, wrong-secret, invalid-subject, and nonexistent-user tokens all produce the same `401` response with `WWW-Authenticate: Bearer`.

`GET /auth/me` returns only `id`, `email`, and `created_at`. `test_auth_deps.py` also verifies that query parameters, request bodies, and spoofed identity headers cannot impersonate another user.

### 4. OAuth2 password login

**Files:** `main.py`, `deps.py`, `requirements.txt`

`POST /auth/login` accepts the standard OAuth2 form fields (`username` as email and `password`). It normalizes the email the same way registration does, verifies the Argon2id hash, and issues a JWT whose `sub` is the decimal string form of `User.id`. Unknown email and incorrect password both return exactly:

```json
{"detail": "Incorrect email or password"}
```

The response contains only `access_token` and `token_type`. `test_auth_endpoints.py` verifies form login, token decoding, subject-to-user mapping, email normalization, indistinguishable credential failures, missing form fields, no password/hash leakage, and the OpenAPI token URL.

### 5. Authenticated task endpoints and ownership

**Files:** `main.py`, `models.py`, `migrate_task_ownership.py`

All `/tasks` routes require the current-user dependency. Task creation takes ownership from the verified JWT, never from the request body. Listing filters by `Task.user_id`, and single-task read/update/delete compare the stored owner with the authenticated user. Another user's existing task returns `403` with `{"detail": "Not authorized to access this task"}`; a nonexistent task returns `404`.

This is actual ownership isolation, verified by both `test_ownership.py` and `test_auth_integration.py`. It is not just an unused `user_id` column.

### 6. Authentication integration suite

**File:** `test_auth_integration.py`

The suite creates a fresh temporary SQLite database per test, registers users through the real endpoint, logs in through the real OAuth2 form, uses the returned JWT as a Bearer token, calls `/auth/me`, and exercises task creation, listing, reading, updating, deleting, and cross-user isolation. It also verifies that the development `taskflow.db` is never used.

# One bug I fixed and why it happened

I did **not** find or fix a genuine runtime bug in the authentication implementation during this audit. All 218 tests pass, and the source code matches the acceptance criteria. I am stating that honestly rather than inventing a failure story.

The real verification issue I found was **documentation drift**: `README.md` line 368 says:

```text
The suite currently contains 161 tests.
```

The actual command output was:

```text
218 passed, 1 warning in 27.85s
```

`README.md` lines 144–145 also say “see the authentication sections below,” but heading inspection found no authentication section in the README. The endpoint table documents `/health` and `/tasks` only, not `/auth/register`, `/auth/login`, or `/auth/me`.

**Observed behavior:** the repository’s documentation understated the suite size by 57 tests and pointed readers to authentication documentation that does not exist, even though the auth code and tests are present.

**Root cause:** the six commits from November 16–21 added `security.py`, `deps.py`, auth tests, and auth routes, but the README was not updated after the last auth mission. The documentation was last aligned with the pre-auth task-only endpoint list and the older 161-test count.

**Fix applied:** none to runtime code. I kept the requested scope to auditing, verification, and the learning log, and did not modify the development database. The README correction is recorded as next week’s first action rather than being mixed into this audit without a corresponding documentation review.

**How regression testing prevents recurrence:** the test suite protects the implemented behavior, but it cannot detect stale prose. Next week I will add the auth endpoints and the correct test count to the README, and make a documentation review part of the weekly catch-up checklist after any endpoint or test-suite change.
